# publish-gated-site — design notes (2026-09-04)

Distilled from moving three sites onto this pattern by hand: a Next.js wiki
portal, an Astro marketing site, and a set of static pitch decks (issue #26).

## Why a release, not a push

Push-to-deploy makes the live site a side effect of editing. For a pre-launch
site — a deck investors will see, a wiki the team reads, a marketing page under
review — that is the wrong default: a half-finished edit is live before anyone
looks. A GitHub release is a deliberate, named, recorded act. It also doubles as
the changelog and the place to attach exports.

The trigger is therefore exactly `release: published`: no `push` and no manual
dispatch. The workflow explicitly checks out the release tag and verifies that
the checked-out commit is the tag's commit before promotion.

## Why the Action only moves a branch

The first version had the Action run `wrangler deploy` with a Cloudflare API
token in GitHub secrets. It works, but it puts a hosting credential in a second
system, and every contributor with Actions access effectively holds it.

Cloudflare Workers Builds inverts the flow: Cloudflare pulls the repo with its
own GitHub App and deploys under a token it manages. The Action's only job is
to fast-forward a `release` branch to the released commit, gated on typecheck,
test and build. Nothing in GitHub can talk to Cloudflare.

The `release` branch is created and moved only by that workflow. A manual
`main:release` push would bypass the release record, so it is not a bootstrap
step.

## Fast-forward vs force

`release` is a pointer. Force-pushing it is the simplest model ("release =
whatever was last published, even if older"), but some repos forbid force-push
outright. The template pushes fast-forward only and fails loudly with the
reason when a release is not ahead of `release`. Rollback is a forward release
from a revert commit. Repos that allow force can flip one line.

The fast-forward variant is also what exposed the shallow-clone bug: with
`--force`, git never has to prove ancestry, so a shallow checkout silently
works — right up until someone switches to fast-forward.

## The gate

GitHub App OAuth with PKCE, then an authorization check: `GET /repos/{repo}`
with the user's token must succeed. Repository read access is the access
control list; nobody maintains a second one. Sessions are HMAC-signed
cookies, four hours, `__Host-` prefixed, always `Secure` (localhost accepts
`Secure`; without it the prefixed cookie is rejected and local OAuth never
completes).

`run_worker_first` is the line that matters in `wrangler.jsonc`. Without it
Cloudflare serves any path that matches a built file before the Worker runs,
and the whole site leaks past the gate. `workers_dev: false` and
`preview_urls: false` keep the custom domain the only origin — which is why
Workers Builds' non-production-branch builds must stay off.

## Safe first publication

The Worker and custom domain need a one-time bootstrap before Workers Builds
can be connected. Bootstrap it with no gate secrets present: every public path
then returns the fail-closed 503 page. Publish the first tagged release next,
let its workflow create `release`, connect Workers Builds to that branch, and
wait for its build to succeed. Only then install the dedicated GitHub App and
set all three Worker secrets. The last secret makes content reachable without
a redeploy, so this ordering guarantees that the first reachable content came
from a release.

"Configuration required" means one or more Worker secrets are absent. Verify
the names with `npx wrangler secret list`; success requires
`GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET`, and `SESSION_SECRET`.

## Allowlist, not blocklist

A repo that is *also* the site usually contains things that must not be
served: sources, exports, docs, tooling. `tools/build-site.mjs` copies an
explicit list into the assets directory and refuses to build if a listed page
has lost its `noindex` tag. Adding a path is a decision; loosening the list is
not a cleanup.

## Bugs encoded here

| Bug | Symptom | Fix in the skill |
|---|---|---|
| Shallow checkout | `! [rejected] … (fetch first)` on the promotion push | `fetch-depth: 0` + `merge-base --is-ancestor` check |
| `wrangler dev` host rewrite | every path 503 on localhost with no secrets | `preview:worker` pins `--host localhost` |
| `"type": "module"` | CommonJS helper scripts crash on `require` | scaffold merges scripts without setting `type` |
| Invisible connect dialog | Cloudflare's dialog in the DOM but not painted | drive it by element ref; noted in SKILL.md |
| Future compat date | wrangler rejects a `compatibility_date` newer than its workerd | known-good default, `--compat-date` to bump |
| Resolver negative cache | `curl` says "could not resolve" right after the DNS record appears | `--resolve host:443:ip`; not a deploy problem |
